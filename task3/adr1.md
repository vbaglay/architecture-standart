### **Решение**  

#### **Диаграмма контекста (C4 Level 1)**  
![Контекстная диаграмма](https://via.placeholder.com/600x300?text=Context+Diagram)  

**Компоненты:**  
1. **Клиентские каналы**:  
   - Сайт (PHP + React.js) для новых клиентов.  
   - Интернет-банк (ASP.NET + MS SQL) для существующих клиентов.  
2. **Промежуточный слой**:  
   - API Gateway + Очередь сообщений (временное решение на RabbitMQ, совместимое с текущим стеком).  
3. **Бэкенд-системы**:  
   - АБС (Oracle + PL/SQL) — хранение ставок и обработка заявок.  
   - Кол-центр (Java Spring Boot + PostgreSQL) — обработка заявок с сайта.  
   - СМС-шлюз — интеграция с внешним телеком-оператором.  

#### **Диаграмма контейнеров (C4 Level 2)**  
![Диаграмма контейнеров](https://via.placeholder.com/600x300?text=Container+Diagram)  

**Ключевые решения:**  
- **Изоляция АБС**: Промежуточный слой (очереди) предотвращает прямые запросы к АБС, снижая нагрузку.  
- **Горизонтальное масштабирование**: Интернет-банк развёрнут в двух ЦОД с балансировкой нагрузки.  
- **Безопасность**: TLS для передачи данных, аутентификация через SMS.  
- **Совместимость**: Использование текущего стека (Java для кол-центра, C# для интернет-банка).

### **Альтернативы**  

| **Альтернатива**                | **Недостатки/Риски**                                                                 |
|----------------------------------|-------------------------------------------------------------------------------------|
| Прямая интеграция с АБС         | Перегрузка БД Oracle, нарушение доступности.                                        |
| Kafka для очередей              | Несовместимость с текущей версией интернет-банка (ASP.NET).                         |
| Микросервисная архитектура      | Высокие затраты на внедрение, отсутствие экспертизы у команды.                      |

---

### **Недостатки, ограничения, риски**  
1. **Ограничения АБС**: Вертикальное масштабирование Oracle может стать узким местом при росте нагрузки.  
2. **Ручная обработка заявок**: На этапе MVP бэк-офис обрабатывает заявки вручную — возможны задержки.  
3. **Зависимость от подрядчиков**: Обновление ядра интернет-банка требует участия внешней команды.  
4. **Риски безопасности**: Данные клиентов с сайта требуют строгой защиты (регуляторные требования).  

---

**Обоснование выбора**:  
- Промежуточный слой на RabbitMQ выбран из-за совместимости с текущим стеком (C#, Java).  
- Горизонтальное масштабирование интернет-банка обеспечит отказоустойчивость даже при сбое ЦОД.  
- Отказ от микросервисов на текущем этапе снижает риски и затраты.
