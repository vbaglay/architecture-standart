## 📝 ADR: Архитектура MVP онлайн-открытия депозитов  

### Название задачи  
Архитектура MVP для онлайн-открытия депозитов (сайт + интернет-банк)

### Автор  
[Ваше имя]

### Дата  
01.05.2025

---

### Функциональные требования (Use Cases)

| №  | Действующие лица или системы | Use Case                            | Описание                                                                                     |
|:--:|:-----------------------------|:-------------------------------------|:--------------------------------------------------------------------------------------------|
| 1  | Клиент (сайт)               | Подача заявки на депозит             | Клиент вводит ФИО + телефон, данные шифруются, заявка уходит в Request Intake Service.      |
| 2  | Клиент (интернет-банк)      | Открытие депозита с SMS-подтверждением | Клиент выбирает счёт и сумму, видит персональную ставку, вводит SMS-код для подтверждения.   |
| 3  | Менеджер кол-центра         | Обработка заявки с сайта             | Менеджер получает заявку в CRM, звонит клиенту, предлагает индивидуальные условия.          |
| 4  | Менеджер бэк-офиса          | Согласование ставки в АБС            | Вводит согласованную ставку в АБС вручную, инициирует SMS-уведомление.                     |
| 5  | АБС                         | Хранение и учёт ставок               | Централизованное хранение ставок вместо XLS, аудит изменений.                              |
| 6  | SMS-сервис                  | Уведомление клиента                  | Отправляет SMS при изменении статуса и после открытия депозита.                            |

---

### Нефункциональные требования

| №  | Требование                                                                                       |
|:--:|:-------------------------------------------------------------------------------------------------|
| 1  | **Доступность 24/7** (uptime 99.9%) — резервный ЦОД, автоматическое переключение.                |
| 2  | **Шифрование трафика** — TLS/HTTPS для всех публичных API и форм.                                |
| 3  | **Изоляция АБС** — запрет прямого доступа, только через промежуточный слой (очередь или API).    |
| 4  | **Совместимость со стеком** — .NET Framework, MS SQL, Oracle, React.js, Java Spring Boot.       |
| 5  | **Масштабируемость ИБ** — горизонтальное масштабирование и балансировка между ЦОД.                |
| 6  | **Производительность UI** — отклик < 500 мс (кэширование, асинхронные запросы).                  |
| 7  | **Расширяемость** — документация, модульность, возможность подключения микросервисов в будущем.   |
| 8  | **Разделение доступа** — бэк-офисы депозитов и кредитов работают независимо (без пересечений).    |
| 9  | **Офлайн-верификация** — обязательное посещение отделения для идентификации новых клиентов.      |

---

### Решение

**Ключевая идея**  
Внедряется промежуточный сервис — **Request Intake Service** (RIS) — для приёма заявок и маршрутизации:

- Сайт и интернет-банк отправляют заявки в RIS по HTTPS.  
- RIS хранит заявки в MS SQL, передаёт в кол-центр (REST) и в АБС (JDBC/REST).  
- АБС обрабатывает вручную (MVP), затем отправляет SMS через SMS-сервис.  
- RIS обеспечивает авторизацию, валидацию, шифрование и логирование.

@startuml C4_Container
!define C4P https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master
!includeurl C4P.puml

Person(client, "Клиент", "Подаёт заявки через сайт или ИБ")

System_Boundary(bank, "Банк «Стандарт»") {

  Container(site, "Сайт", "PHP + React.js", "Форма выбора депозитов и заявки") {
    ContainerDb(site_db, "MySQL/PostgreSQL", "Хранит часть CMS-данных")
  }

  Container(ib, "Интернет-банк", "ASP.NET MVC + MS SQL", "Подача и отслеживание заявок") {
    Container(ib_ui, "UI", "Razor + JS", "Формы и клиентская логика")
    Container(ib_app, "Application", "C#/.NET", "Валидация, авторизация, интеграция с RIS")
    ContainerDb(ib_db, "MS SQL", "Сессии, кэш справочников")
    Rel(client, ib_ui, "HTTPS")
    Rel(ib_ui, ib_app, "API вызовы")
    Rel(ib_app, ib_db, "CRUD")
    Rel(ib_app, ris, "REST API", "JSON/HTTPS")
  }

  Container(ris, "Request Intake Service", "ASP.NET Web API + MS SQL", "Приём, логирование, маршрутизация") {
    ContainerDb(ris_db, "MS SQL", "Хранение заявок и статусов")
  }

  Container(ctr, "Кол-центр CRM", "Java Spring Boot + PostgreSQL", "Рабочая панель менеджера") {
    ContainerDb(ctr_db, "PostgreSQL", "Заявки и история взаимодействий")
    Rel(ris, ctr, "REST API", "JSON")
  }

  Container(abs, "АБС", "Delphi Desktop + Oracle", "Учёт депозитов и ставок") {
    Container(abs_ui, "Desktop Client", "Delphi", "Интерфейс бэк-офиса")
    Container(abs_proc, "PL/SQL Procedures", "Oracle", "Логика расчёта ставок и хранения")
    ContainerDb(abs_db, "Oracle", "Операционные данные")
    Rel(ris, abs_proc, "JDBC", "Синхронная передача заявок")
    Rel(abs_proc, abs_db, "Reads/Writes")
    Rel(abs_ui, abs_proc, "Calls Procedures")
  }

  Container(sms, "SMS-сервис", "REST API", "Отправка SMS") {
    Rel(abs_proc, sms, "REST API", "Запрос на отправку")
    Rel(sms, client, "SMS")
  }

  Rel(site, ris, "REST API", "JSON/HTTPS")
}

@enduml

Альтернативы
Решение	Недостатки / Риски
Прямая интеграция ИБ → АБС	Перегрузка Oracle, нарушение SLA, отсутствие очередей.
Использование Kafka	Несовместимо с текущей ИБ, нет экспертизы, высокая стоимость миграции.
Полная микросервисная архитектура	Сложность внедрения, высокая начальная стоимость, не подходит для MVP.

Недостатки, ограничения и риски
Ручная обработка ставок в АБС — риск задержек и ошибок.

Узкое место АБС (вертикальное масштабирование).

Зависимость от подрядчика при изменении ядра ИБ.

Риски безопасности — данные клиентов требуют строгой защиты (ПДн).
