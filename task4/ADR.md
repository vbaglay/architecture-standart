### <a name="_qmphm5d6rvi3"></a>**Решение**
Приведите диаграммы контекста и контейнеров в модели C4. Опишите там основные компоненты и интеграции всех элементов решения. 


Логика архитектурных решений и выбора технологий

1. Функциональные требования
Чтобы не вносить изменения в АБС выбрал отдельный сервис экспорта. Чтобы не нагружать АБС отдаем данные по расписанию и используемкомпетецию внутри банка.
Кол-центр забирает ставки через АПИ, что ускорит процесс. Партнерский-центр стягивает данные с sftp сервера, куда их выгружает exportservice. 
разграничение доступа по модели rbac через oauth20+mTLS. Передача через SFTP (по расписанию), в формате CSV, с PGP-шифрованием.
Консультация клиента по телефону	Простота доступа к ставкам для консультанта через CRM, быстрый отклик, только утверждённые данные.
Ручная корректировка ставок	Интерфейс в АБС с сохранением истории через Oracle-триггеры.

Нефункциональные требования
Отсутствие прямых вызовов к АБС.
Безопасность передачи данных	PGP для файлов, TLS/SSL для REST API и SFTP; OAuth2 + сертификаты.
Высокая доступность и SLA (99%)	Использование SFTP-сервера с мониторингом через Prometheus + Grafana.
Совместимость с текущим стеком	Выбор технологий только из уже используемых в банке (C#, Oracle, PL/SQL, Java).
Отказ от внедрения Kafka на этапе MVP	Использована проверенная архитектура на файлах и REST API; Kafka — в будущей версии.
Используются существующие протоколы и решения (SFTP, PGP), не требующие внедрения сложной инфраструктуры.

3. масштабируемость и расширяемость
Модульность: сервис экспорта реализован как отдельный компонент, не зависящий от CRM или АБС.
Гибкость обновлений: добавление новых каналов распространения ставок возможно без изменения АБС.



### <a name="_bjrr7veeh80c"></a>**Альтернативы**
Опишите здесь наиболее важные альтернативные решения.

### Альтернативы

| Альтернатива                                 | Описание                                                                                         | Недостатки / Риски                                                                                              |
|----------------------------------------------|--------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------|
| **1. Прямая REST-интеграция CRM ↔ АБС**      | CRM напрямую запрашивает ставки из АБС по HTTP(S)                                                | - Перегрузка АБС при пиковых обращениях<br>- Сложность ограничения прав доступа на уровне ставок<br>- Нет буферизации при сбоях |
| **2. Использование очередей сообщений (Kafka)** | Все изменения ставок публикуются в Kafka-топик, подписчики (CRM и партнёры) получают обновления  | - Текущая версия интернет-банка и АБС не поддерживают Kafka<br>- Необходима подготовка инфраструктуры и обучение команды         |
| **3. Ручное распространение Excel-файлов**   | Бэк-офис ежедневно рассылает по почте Excel-файлы с текущими ставками                            | - Высокий риск человеческих ошибок<br>- Отсутствие аудита изменений<br>- Низкая скорость обновления и масштабируемости         |
| **4. Веб-портал для партнёров**              | Развернуть веб-интерфейс, где партнёры могут авторизоваться и просматривать ставки в реальном времени | - Потребуется значительная доработка web-стека<br>- Сложности с безопасностью и разграничением доступа<br>- Более длительные сроки внедрения |
