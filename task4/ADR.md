### <a name="_qmphm5d6rvi3"></a>**Решение**
Приведите диаграммы контекста и контейнеров в модели C4. Опишите там основные компоненты и интеграции всех элементов решения. 


Логика архитектурных решений и выбора технологий

1. Соблюдение функциональных требований (Use Cases)
экспорт ставок	Использование сервиса экспорта, инициирующего выгрузку каждые 2 часа.
Доступ внутреннего кол-центра	REST API с защищённой авторизацией (OAuth2 + mTLS).
Доступ партнёрского кол-центра	Передача через SFTP (по расписанию), в формате CSV, с PGP-шифрованием.
Консультация клиента по телефону	Простота доступа к ставкам для консультанта через CRM, быстрый отклик, только утверждённые данные.
Ручная корректировка ставок	Интерфейс в АБС с сохранением истории через Oracle-триггеры.

2. Архитектурные и нефункциональные ограничения
Перегрузка АБС	Чтение только по расписанию; отсутствие прямых вызовов от CRM или внешних систем к АБС.
Безопасность передачи данных	PGP для файлов, TLS/SSL для REST API и SFTP; OAuth2 + сертификаты.
Высокая доступность и SLA (99%)	Использование SFTP-сервера с мониторингом через Prometheus + Grafana.
Совместимость с текущим стеком	Выбор технологий только из уже используемых в банке (C#, Oracle, PL/SQL, Java).
Отказ от внедрения Kafka на этапе MVP	Использована проверенная архитектура на файлах и REST API; Kafka — в будущей версии.

3. масштабируемость и расширяемость
Модульность: сервис экспорта реализован как отдельный компонент, не зависящий от CRM или АБС.
Гибкость обновлений: добавление новых каналов распространения ставок возможно без изменения АБС.


4. Снижение зависимости от внешних подрядчиков
Все доработки реализуемы силами внутренних команд: SMS и выгрузка, REST API, CRM-интеграция.

Используются существующие протоколы и решения (SFTP, PGP), не требующие внедрения сложной инфраструктуры.


### Логика выбора технологий и архитектурных решений

#### 1. **Гибридная модель шифрования (PGP + SFTP/SSL)**
- **Функциональные требования**: 
  - F1 (экспорт ставок), F3 (передача партнёрам)
- **Нефункциональные требования**: 
  - N1 (безопасность), N4 (разделение доступа)
- **Обоснование**:
  - PGP обеспечивает end-to-end шифрование файлов даже при компрометации SFTP-сервера.
  - SFTP+SSL защищает канал передачи. Альтернативы (AS2/HTTPS) требовали бы переработки legacy-систем партнёров.

#### 2. **Сервис экспорта на C#/.NET**
- **Функциональные требования**: 
  - F1-F4 (обработка ставок)
- **Нефункциональные требования**: 
  - N3 (совместимость), N2 (SLA 99%)
- **Обоснование**:
  - Использование существующего стека банка (.NET + Oracle) минимизирует риски внедрения.
  - Поддержка Quartz.NET для планирования выгрузок и Polly для обработки сбоев.

#### 3. **Асинхронная модель работы с АБС**
- **Функциональные требования**: 
  - F4 (корректировка ставок)
- **Нефункциональные требования**: 
  - +R2 (запрет прямой нагрузки на АБС)
- **Обоснование**:
  - ODBC + PL/SQL вместо прямых SQL-запросов снижает нагрузку на АБС.
  - Триггеры аудита в Oracle реализуют нефункциональное требование R3 (устойчивость к потере данных).

#### 4. **OAuth2 + mTLS для API**
- **Функциональные требования**: 
  - F2 (доступ кол-центра)
- **Нефункциональные требования**: 
  - N1 (безопасность)
- **Обоснование**:
  - mTLS исключает MITM-атаки, OAuth2 предоставляет гибкие роли (консультант/админ).
  - Альтернатива (JWT) не обеспечивает проверку клиентских сертификатов.

#### 5. **Prometheus + Grafana для мониторинга**
- **Нефункциональные требования**: 
  - N2 (SLA 99%), P2 (производительность)
- **Обоснование**:
  - Интеграция с существующей инфраструктурой банка.
  - Возможность настройки кастомных алертов (например, при падении скорости выгрузки).

#### 6. **Отказ от Kafka в пользу SFTP**
- **Ограничения**: 
  - +R6 (несовместимость с текущим ИБ)
- **Обоснование**:
  - SFTP поддерживается всеми партнёрами, не требует обновления их систем.
  - Kafka потребовала бы перевода интернет-банка на микросервисы (нарушение +R7).

---

### Критические trade-offs:
1. **Скорость vs. Безопасность**:
   - Выбор PGP (медленнее AES) обусловлен требованием N1. Компенсируется кэшированием ставок в CRM.

2. **Гибкость vs. Совместимость**:
   - REST API для внутреннего кол-центра (гибкость) vs. CSV для партнёров (совместимость).

3. **Автоматизация vs. Контроль**:
   - Автоматические выгрузки (+R5) но с ручной корректировкой ставок (F4) для соблюдения регуляторных требований.
